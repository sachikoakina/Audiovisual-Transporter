# 待核对名单：用 90 天 Artifact 跨轮维护

> **2026-10-25 起多了一个对账入口**：`sync.yml` 现在把同一轮的 `PathReport` 以 JSON 上传为 `sync-report-<run_id>`，名单作业会下载它、在摘要末尾追加一节「运行报表（JSON）」，比较「本轮实际计了多少 failed」与「日志解析出多少」。**名单内容仍由日志决定**——这一节只提示差值，不增删条目。缺 artifact 时该节整体不出现（旧运行、上传失败都走这条路）。
>
> 基线 `main@e13c482`。机制本身仍是两个文件：`.github/workflows/review-queue.yml`（触发器）与 `scripts/review-queue.mjs`（解析 + 状态机 + 渲染）。`.github/workflows/sync.yml` 现在多了一个 `if: always()` 的「发布作业摘要」步骤（与名单无关，见 `docs/reference.md` 的「CI 中的作业摘要」）；`src/` 的改动仍限于展示与日志层 —— ② 补了一条未匹配日志、⑤ 的条目级失败换了措辞，不涉及写入目标端的行为与退出码。

## 1. 目标与硬约束

| 约束                               | 落地方式                                                                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 不改动现有代码逻辑                 | 机制读取日志与 `sync-report.json`、只写自己的 artifact；`src/` 的改动限于展示与报表（新增 `scannedIds`、② 的未匹配日志、⑤ 的失败措辞），不动任何写入目标端的行为与退出码 |
| 仅用 Actions Artifact 作临时存储   | 每轮上传一份 `review-state`，`retention-days: 90`                                                                                                                        |
| 数据不经过本地设备                 | 下载日志、合并、上传全在 runner 内完成                                                                                                                                   |
| 不产生费用                         | 单份快照约 3–20 KB，90 天 × 39 轮 ≈ 0.1–1 MB，远低于账户 500 MB 的 Actions 存储额度                                                                                      |
| 跨轮同一性 / 去重                  | key = `source::(url │ bangumi-id │ title)`，命中即更新而非新增                                                                                                           |
| 被扫描到且匹配成功后移除、增量更新 | 连续两轮「被扫描到且未再出现」才删除；未覆盖的条目冻结，`firstSeenAt` 保留，`seenCount` 递增                                                                             |

## 2. 为什么是这个形状（以及它付出的代价）

`sync` 结束前，runner 里能代表「这一轮发生了什么」的有两样东西：**控制台日志**（打印过哪些条目）和 `sync-report.json`（每条链路完整检查过哪些条目，即 `PathReport.scannedIds`）。结构化留档文件 `.cache/unmatched.json` 仍不跨轮存在、也不会被上传，因此名单的**条目内容**来自日志；**是否允许淘汰**来自报表的扫描集合 —— 缺一行日志有歧义，扫描集合命中没有。

这不是设计缺陷，是约束的直接后果。想清楚它的边界，比假装覆盖完整更有用：

| 链路            | unresolved                                                          | failed                                                                                   | skipped                                          |
| --------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------ |
| ① 豆瓣→Notion   | 无此概念                                                            | ✅ 逐条（`标题[链接] — reason`）                                                         | ◐ 缺库 ✅／白名单剪除 ✗                          |
| ② 豆瓣→NeoDB    | ✅ 标题 + 豆瓣链接（`No NeoDB match, skip:`）                       | ✅ `neodb-mark-rejected`                                                                 | ✅ 目标端守卫（含标题）／白名单 ✗                |
| ③ 豆瓣→Bangumi  | ✅ 含豆瓣链接                                                       | ✅ `bangumi-write-rejected`                                                              | ✅ 目标端守卫（`subject/N`）                     |
| ④ Bangumi→NeoDB | ✅ 名称 + Bangumi 链接（`标题[链接]`，2026-10-26 起；此前只打 URL） | ✅ 逐条（catch 打印标题）                                                                | ✗ 平台不符静默                                   |
| ⑤ NeoDB→TMDB    | ✅ 标题（无 id，key 靠标题）                                        | ✅ `tmdb-item-threw` / 评分与 watchlist 写失败；◐ 无目录条目的名字是 `(unknown)`，只计数 | ◐ `Mark without a catalog item` 无标题，无法归属 |

> **2026-10-25 之后**：明细行不再按「① 的三条专用规则」认领，而是**按 reason slug 路由**。`src/` 里每个 `failedItems` / `skippedItems` 条目都带一个 slug，控制台明细打的是 `· 标签 — slug`，`scripts/review-queue.mjs` 的 `DETAIL_REASONS` 把它映射回「哪条链路 + 哪一档」。因此上表里 ②③⑤ 的 failed 也从「静默」变成了 ✅——它们本来就打印，只是没被认领。
>
> 两条刻意的留白：**slug 被多条链路共用的不猜**（`category-not-allowed` 属 ①②③、`guard-target-status` 属 ②④），名字是 `(unknown)` 的也不收（一条叫 "(unknown)" 的条目会同时代表所有无名失败，且永远勾不掉）。两者都计入名单顶部的「另有 N 处…无法归属」计数，而不是悄悄丢掉。

上表的五行也是名单的五个一级分组，顺序固定 ①→⑤：`Douban → Notion`、`Douban → NeoDB`、`Douban → Bangumi`、`Bangumi → NeoDB`、`NeoDB → TMDB`。这些字符串与 `src/paths/*.ts` 里的 `LABEL` 逐字相同，因此同一条链路在控制台日志、作业摘要、待核对名单里是同一个词，可以直接 grep 对齐。

两条已知截断：`printPathSummary` 的标题清单上限 20（`src/sync-report.ts:25`），主要影响 ④；⑤ 的标签是 `display_title`（`src/paths/neodb-to-tmdb.ts:382`），所以它只能靠标题建 key——**改标题会让它看起来像新条目**。这一条在 ③ 不存在，因为 ③ 的标签带豆瓣链接。

> **2026-10-28 之后，⑤ 的 `unresolved` 有三种来源，名单只看见一种。** 控制台仍然是同一句 `No TMDB match; skip X.`（名单按它采、`verify-log-contract` 锁着它），区别在留档 `.cache/unmatched.json` 的 `reason`：`no-tmdb-match`（搜过了，TMDB 没有）、`no-neodb-year`（NeoDB 侧没有年份，所以**根本没搜**）、`no-neodb-year-fetch-failed`（取年份的请求失败）。这样一条「没被搜过的条目」不会伪装成「搜过而没找到」，但代价是**名单上看不出这个区别** —— 要看就得读留档或把日志级别开到 `debug`。判据见 [`decisions.md`](./decisions.md) §11。

## 3. 名单结构

名单是两级：**链路 → 档位**。链路顺序固定 ①→⑤，档位顺序固定 `unresolved` → `failed` → `skipped`，只输出非空的分组。

**`本轮新增` 与 `本轮移除` 是同一个结构**（H2 = 变化类型，H3 = 链路，带本组条数），只是条目行一个是普通文字、一个名字加删除线。两节共用同一个渲染函数，所以它们不会各自长歪；`观察中` 是唯一不分组的附属小节，链路标在行尾。

```text
# 待核对名单（46 条）                    ← 名单条目总数
本轮运行：… / 计数行 / 降级提示           ← 原样保留
## 本轮新增                              ← H2 = 变化类型
### Bangumi → NeoDB（2）                  ← H3 = 链路，①→⑤，带本组条数
- `unresolved` 狐妖小红娘13 黄风岭篇 — https://bgm.tv/subject/391457 · neodb-unresolved
## 本轮移除（已连续两轮未出现）              ← 与「本轮新增」同形
### Douban → NeoDB（1）
- `unresolved` ~~天仙配~~ — https://book.douban.com/subject/2/ · no-neodb-match
## Douban → Bangumi                      ← 主名单：H2 = 链路
### unresolved（2）                       ← H3 = 档位，仅输出非空档位
- [ ] **1.** 四郎探母 — https://movie.douban.com/subject/1/ · no-bangumi-match · 已存在 3 天
- [ ] **2.** 天仙配 — https://movie.douban.com/subject/2/ · no-bangumi-match · 已存在 3 天
## NeoDB → TMDB
### unresolved（44）
- [ ] **1.** Medalist (金牌得主 第二季) · no-tmdb-match · 已存在 0 天
## 观察中（2，下一轮仍出现才入名单）        ← 附属小节：不分组、不编号，链路标在行尾
- `failed` 摔跤吧！爸爸 — https://movie.douban.com/subject/3/ · bangumi-write-rejected（Douban → Bangumi）
---
脚注（原样保留）
```

| 规则      | 说明                                                                                                                                                                                                                                           |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 链路顺序  | 固定 ①→⑤，不按条数排序 —— 两轮之间可以直接对照。主名单、`本轮新增`、`本轮移除` 三处共用同一条排序规则与同一组显示名                                                                                                                            |
| 档位顺序  | `unresolved` → `failed` → `skipped`；空档位不产生 H3，也不留空行                                                                                                                                                                               |
| 条目行    | **名称在前、链接在后**（`名称 — 链接 · reason`）。只打一个地址等于没说清要核对哪一条；④ 的行在 2026-10-26 之前正是如此。名称退化成 URL 时（旧日志、旧快照）不重复打印地址                                                                      |
| 编号      | 只在主名单的档位下有，每个 H3 内从 1 开始，是「本节第几条」，不是全局序号；引用时请连链路与档位一起说。序号写在**条目正文**里（`**3.**`），不是列表标记 —— 原因见下面「复选框」一行                                                            |
| 组内顺序  | 等于 `state.json` 的 `items` 顺序（先沿用旧序、新增追加），渲染不重排 —— 条目不会在两轮之间跳位。`本轮新增`/`本轮移除` 没有这样的历史顺序可依，取「出现在日志里的先后」                                                                        |
| 未知 slug | `source` 不在映射表里时**原样作为标题显示名**，排在五条链路之后。这是兜底：一旦出现就说明 `SOURCE_LABELS` 漏了一项，而不是被伪装成一个正常标题                                                                                                 |
| 复选框    | `- [ ] **N.** 标题` 是 GFM 任务项。序号必须进正文：GitHub 给任务列表项设了 `list-style-type: none`，标记位让给方框，所以 `1. [ ] 标题` 这种写法渲染后只剩一排方框、看不到任何编号。面板是静态渲染，方框**不可点击**，复制进 issue 正文才可勾选 |
| 删除线    | `本轮移除` 只给**名字**加删除线，链接保持可点 —— 「它真的匹配上了吗」正是移除会引出的问题                                                                                                                                                      |
| 出现次数  | **不显示**。`seenCount` 只决定条目是否过了观察期（`MIN_ROUNDS`）与何时移除（`MISSES_BEFORE_REMOVAL`），写进正文只会让读者去反推一个自己动不了的阈值                                                                                            |
| 附属小节  | `观察中` 不分组、不编号，行式与新增/移除相同，链路标在行尾括号；还在观察期里的条目**只**出现在这里，不再同时出现在 `本轮新增`（否则同一份摘要里每条首轮 `failed` 都会出现两次，`新增 N` 也数不清）                                             |
| 体量      | 46 条约 15 KB；`**N.**` 每行多约 7 字节、46 条约 +0.3 KB，两级标题开销 < 1 KB（H2 ≤5、H3 ≤15），远低于 issue 正文 65536 字符上限                                                                                                               |

## 4. 状态机

```mermaid
stateDiagram-v2
  [*] --> 观测: 本轮日志解析出条目
  观测 --> 名单: 首次出现（failed 需连续两轮）
  名单 --> 名单: 再次出现 → seenCount+1, missedRuns=0
  名单 --> 观察缺席: 在扫描集合内但未出现 → missedRuns=1
  观察缺席 --> 名单: 又出现
  观察缺席 --> 名单: 本轮未被扫描 → missedRuns=0（冻结）
  观察缺席 --> [*]: 连续两轮被扫描到且未出现 → 移除
  观测 --> 冻结: 报表计了未匹配、日志却一条都没解析到
  冻结 --> 名单: 名单原样保留，摘要报警
```

三个数值决定一切：

- `firstSeenAt`：只在新条目上写入，之后永不覆盖 —— 这是「这条我盯了多久」的唯一依据；
- `missedRuns`：**在扫描集合内**但未出现一次 +1，出现即清零；不在集合内则清零（缺席没有被观察到），**到 2 才删除**（一次抖动不该删条目）；
- `seenCount`：出现次数，`failed` 用它实现「观察期」（`MIN_ROUNDS.failed = 2`）。

**扫描集合**：`PathReport.scannedIds` 是每条链路本轮真正检查过的条目身份，按链路构造报告时写入。它与名单的 key 身份段同形：① 是豆瓣链接与 `config:<分类>`，②③ 是豆瓣链接，④ 是 Bangumi 条目 URL（另加标题，供按标题建 key 的失败行），⑤ 是展示标题。被 `SYNC_MAX_ITEMS` / `NEODB_MAX_PAGES` 截断、因 401 中止、或整条链路没运行的条目都不会进入集合 —— 它们在名单里被冻结，而不是被读成「已修好」。

**降级保护**：如果本轮解析出 0 条而上一份名单非空，且报表仍计了未匹配条目，说明更可能是解析器失效而不是问题全修好了。此时冻结名单、不计数、在摘要顶部标红。若报表也计 0 条，沉默是真的，被覆盖的条目可以正常老化。这条比多解析几个字段重要得多——一个会把自己清空的监控，比没有监控更危险。没有报表时覆盖集合为空，缺席一律冻结，摘要另有一行说明。

## 5. Artifact 作为状态载体

```mermaid
flowchart LR
  S[sync 运行结束] --> T[workflow_run: completed]
  T --> R[按 name 列出 artifact<br/>取未过期的最近一份]
  R --> M[合并 + 淘汰 + 渲染]
  T --> L[REST 下载该轮日志包]
  T --> J[下载 sync-report-&lt;run_id&gt;]
  L --> P[解析本轮条目]
  J --> C[每条链路的 scannedIds]
  P --> M
  C --> M
  M --> U[upload-artifact<br/>name: review-state<br/>retention-days: 90]
  M --> Y[GITHUB_STEP_SUMMARY<br/>零权限、零存储]
```

- **artifact 不可变、同名每轮唯一**，所以不能追加；每轮上传一份完整快照，下一轮用 `GET /repos/{repo}/actions/artifacts?name=review-state` 取 `expired == false` 中最新的一个，再 `.../artifacts/{id}/zip` 下载。
- **报表缺失是安全侧**：`sync-report-<run_id>`（保留 7 天）下载失败、或来自本机制上线前的运行，`scannedIds` 就是空的。此时名单只更新、不移除，摘要写明「没有运行报表」。这不是故障，而是「没看全就别删」的直接后果。
- `retention-days: 90` 只能**缩短**仓库设置，不能延长；公开仓库上限就是 90，私有仓库可到 400。请保持 Settings → Actions → Artifact and log retention ≥ 90。
- 链式依赖：只要 cron（周一三五）还在跑，最长间隔 3 天，永远不会落到 90 天之外；停跑超过 90 天才需要从空名单重建（`firstSeenAt` 重置，条目会重新入列）。
- 费用：单份 3.4 KB（7 条实测）；39 轮/90 天 ≈ 130 KB。即使名单涨到 50 条（约 14 KB），累计仍 < 1 MB，不触达 500 MB 免费额度。

## 6. 权限

```yaml
permissions:
  contents: read # 只读仓库，取默认分支上的脚本
  actions: read # 唯一新增：下载别的 run 的日志与 artifact
```

下载别的 run 的日志/artifact 必须显式给 `actions: read`（`GITHUB_TOKEN` 默认对当前 run 之外不可见）。没有 `issues`、没有 `contents: write`：本机制不写仓库任何内容。

| 观察期不重复       | 首轮 `failed` 只出现在 `观察中`，`本轮新增` 计数为 0 且整节不出现                                                                         |
| `prettier --check` | `.mjs` / `.yml` clean；Windows 检出为 CRLF 时需 `--end-of-line crlf`                                                                      |

## 8. 已知局限与补齐路径

| 局限                       | 补齐代价                                                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `skipped` 只看到守卫与缺库 | 在源头区分白名单/增量/分类/重复（约 20 行）；`category-not-allowed` 被 ①②③ 共用，得先拆 slug                      |
| ⑤ 的 key 依赖标题          | 日志里改打 uuid（1 行）；目前改标题会留下旧条目（不再误删），需人工清理                                           |
| 未覆盖的条目不淘汰         | 需要一次全量运行或人工清理；这是「不误删」的直接代价，不是缺陷                                                    |
| 旧报表没有 `scannedIds`    | 该轮按空覆盖处理，只更新不移除；下一次同步产生的新报表即恢复                                                      |
| ⑤ 的条目没有链接           | `No TMDB match; skip <标题>` 只打标题；NeoDB 条目的 `url` 在 `item` 上但没进日志，要链接得改那一行（同 ④ 的改法） |
| 旧快照里的 ④ 条目没有名称  | 2026-10-26 之前写入的 `review-state` 里 `title` 就是 URL，只能等它自己消失（≤ 90 天）                             |
| 无名条目只能计数           | ⑤ 的 `(unknown)` 与 `Mark without a catalog item` 两条日志本来就没带名字，要在 `src/` 里补                        |

第一、二条只需**追加记录**，不改变任何写入目标端的行为与退出码。③ 的 failed、② 的 unresolved、⑤ 的条目级失败已在 2026-10-25 补齐，不再列在这里。

## 9. 退出条件：对账转正

本节记录这套机制的**终点**，避免「日志是真源」变成永久状态（决策原文见 `docs/decisions.md` §9）：

1. **观察期**：`sync-report.json` 与日志解析并行，每轮摘要末尾给出对账小节。报表现在同时提供 `scannedIds`（覆盖范围），名单据此决定是否允许淘汰；日志仍是条目内容的来源。
2. **判据**：连续 ≥5 轮差值行为零（没出现 ⚠️），且 `stats.json` 的 `runReport` 每轮非空。
3. **切换**：名单改由 JSON 生成；日志解析保留为备份与人工可读的旁证。
4. **切换时必做**：按新真源重验 `MIN_ROUNDS`；去重键从「解析出的标题」换成 `url`，并核对历史 `review-state` 的合并语义（不能靠自然收敛）。

未满足判据前不切换 —— 理由与当初拒绝一步替换相同：差异必须可归因。
