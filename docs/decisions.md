# 决策记录

这里记的是**为什么这样做**，而不是**怎么做**——后者在代码注释里。每条决策都写明当时的替代方案与被否掉的原因，目的是让下一个改这块的人先看见约束，再动手。

背景与逐条审阅过程见 [`refactor-review.md`](./refactor-review.md)；本文只留结论。

## 1. 读取失败用异常，不用返回值（2026-10-25）

**决策**：目标端读取有 `found` / `absent` / `error` 三种结果（`ReadResult<T>`），前两者由 `paths/read.ts` 翻成「值 / `null`」，`error` 翻成异常：`auth` 抛 `PathAbortedError`（整条链路停），其余抛 `ItemReadError`（只这一条失败）。

**为什么不是再返回一个布尔值**：上一个 bug 就是「返回值被忘记检查」——`bangumi-to-neodb.ts` 里 `await markNeodbItem(...)` 之后无条件 `markWritten = true`，于是 NeoDB 的拒绝被记成成功，退出码、明细、待核对名单三处同时失明。抛出的东西不会被忽略；没人接就当场崩，对「目标端不肯告诉我现状」来说这是正确的失败形态。

**为什么不是抛错就 abort**：单条 500 与 token 失效是两件事。前者该跳过这一条继续，后者该停下——一次过期 token 会产出几百条 `failed` 明细，把名单刷爆。

## 2. 只有 `absent` 允许被覆盖（2026-10-25）

**决策**：404 在「未标记 / 未收藏」这类端点上归为 `absent`（可以据此新建），在「记录本身不存在」的端点上归为 `error`（什么都不写）。规则是纯函数 `classifyReadFailure`，由断言保护。

**为什么这条值得单列**：`null` 曾经同时代表「没有」与「读不到」，而两者的写计划相反。`tmdb_prefer` 的保护条件 `existingRating !== null` 因此在一次 500 之后失效，直接覆盖用户在 TMDB 手设的评分。这类 bug 不会报错，只会少一个评分。

**配套**：`planTmdbWrites` 与 `extractTmdbRating` 的参数不再接受 `null`——规则层从此无法把「读失败」表达成「无评分」。

## 3. 计数按条目，不按字段（2026-10-25）

**决策**：⑤ 的 `written` 与 `failed` 都按条目计；评分 / watchlist 的字段级数字只出现在分项明细里。

**为什么**：自检等式 `scanned = written + unchanged + skipped + unresolved + failed` 是对**条目**求和的。原先 `written = writtenRating + writtenWatchlist`，一个条目写两个字段就给左边加 2，于是「评分与 watchlist 都写」的运行必然打出一个 `✘`——而一个会在正确运行时报警的自检，教人忽略所有 `✘`。

**代价**：作业摘要里 ⑤ 的 `written N` 会变小。这是语义变更，已在此记录。

## 4. dry-run 必须自称 dry-run（2026-10-25）

**决策**：`PathReport.dryRun` 进汇总，状态列写 `dry-run`，路径行写 `— dry run, nothing was sent`；计数仍是「本来会写什么」。

**为什么不是干脆不计数**：不计数会让自检等式在 dry-run 下破掉，那是另一个谎。让数字留在原处、再用一个词说明它是什么，比让两个地方都失真更好。

## 5. 待核对名单按 reason slug 路由，共用 slug 不入表（2026-10-25）

**决策**：`scripts/review-queue.mjs` 的 `DETAIL_REASONS` 只收**唯一归属**的 slug；共用 slug（`category-not-allowed` 属 ①②③）与未登记 slug 一律计入 `unattributable`，名单顶部用文字说明有多少条无法归属。

**为什么不做二级猜测**：「这条 `category-not-allowed` 大概来自哪个路径」猜错比不猜更坏——猜错会把一条失败记到不该看的链路名下，而「无法归属」至少是真的。上一轮 ④/⑤ 共用 `Item failed, continuing:` 就正是这种错：⑤ 的失败全被记到 ④ 名下。

**配套**：`npm run verify:log-contract` 断言每个 slug 仍由它声称的链路产出、且没有第二个归属；改名或搬家会让它变红，而不是让名单悄悄变空。

## 6. 运行时消息用英文，401 用用户的语言（既有约定，2026-10-25 补齐理由）

**决策**：普通运行时消息是英文；三条鉴权失败消息（NeoDB / Bangumi / TMDB 的 401）刻意用中文，并给出确切的修复步骤。中文注释 + 英文消息是代码里的常规形态。

**为什么 401 例外**：401 的读者是**运行者**，他要做的是去某个页面重新授权，而那条指令用母语写才不会被跳过。这条理由原先只写在三条实现中的一条里，另外两条只是照抄——现在三处都有。

## 7. 失败走报告，不走旁路布尔量（既有约定，2026-10-25 补记）

**决策**：一条链路的失败只能表达为 `PathReport` 的字段（`aborted` / `failed` / `tolerated`），任何「顺手记一个标志位」的写法都不接受。

**为什么**：曾经有一次，豆瓣 RSS 抓取失败被记在一个旁路布尔量上，于是收尾汇总打出「全部成功」，而进程以 1 退出——同一件事在三个地方给出三个答案。改成报告之后，汇总、作业摘要与退出码同源，它们不可能互相矛盾。

**判据**：如果某个事实会同时影响「打印什么」和「退出码是多少」，它就必须只有一个来源，而且必须是那个两者都读的来源。

## 8. 注释双语，且不压缩成「一句 why」（2026-10-25）

**决策**：英文段 + 中文段成对保留。

**为什么**：抽查三组（`types.ts` 的 `processed`、`sync-report.ts` 的 `printOverallSummary`、`douban-to-bangumi.ts` 的 `recordUnresolved`）全部是**逐段互译**，即「两个读者、同一份信息」。真正的冗余不在这里，而在**事故复盘**类注释（「原先有 3 处 `process.exit(1)` 会连带杀掉剩余分类」）——那类应该进 `git log`，而**约束类**注释（为什么这里必须返回报告而不是抛错、为什么配额不能数 `scanned`）必须留在代码旁边，因为它约束的是「下一行该怎么写」。

**判据**：注释能否被删掉而不改变别人写代码的方式。能删的是叙事，不能删的是约束。

## 9. 对账转正的退出条件（2026-10-25 立）

**决策**：`sync-report.json` 与日志解析并行期为**观察期**，不是终点。连续 **≥5 轮** 对账小节零差值（即「报表 failed 数 ≤ 日志解析数」从未触发 ⚠️），且 `stats.json` 里 `runReport` 每轮非空，则按 strangler 收尾：名单改由 JSON 生成，日志解析降级为备份。

**为什么需要写下来**：一步替换无法归因（改完名单内容变了，没人说得清是哪一处造成的），所以并行是对的；但并行没有退出条件就会变成永久双轨 —— 那时日志文案仍是真源，「隐性接口」只是被推迟，不是被退役。

**切换时的两件必做**：`MIN_ROUNDS` 要按新真源重验（它是按「连续几轮出现」定义的）；去重键要从「解析出的标题」换成 `url`，历史 `review-state` 的合并语义必须显式核对一次，而不是让它自然收敛。

## 10. ④ 保留裸 `item-threw`，不与 ② 的 `neodb-mark-rejected` 合并（2026-10-25 立）

**决策**：④ 的写入被拒继续走 `item-threw: <message>`，不新增独立 slug。

**为什么看似不一致却只能这样**：`neodb-mark-rejected` 在 `DETAIL_REASONS` 里归属 **② Douban → NeoDB**。名单的路由键是 slug，因此 ④ 若打同一个 slug，它的条目会被记到 ② 名下 —— 那正是 `f50e6e2` 修掉的那类病（④/⑤ 曾共用 `Item failed, continuing:`，⑤ 的失败全记到 ④ 头上）。而「按来源加前缀」（如 `bangumi-neodb-mark-rejected`）会给同一个事件造出第三种拼法，比现状更不利于 grep。

**判据**：slug 的唯一归属是硬约束，命名一致性是软目标。两者冲突时，唯一归属优先 —— 跨链路统计这类需求应该用 `sync-report.json`（`source` 是字段），而不是靠 slug 拼写。

## 11. 没有年份就不进标题搜索，而不是「只比标题」（2026-10-28 立）

**决策**：⑤ 的第 3 级（标题搜索）要求 NeoDB 与 TMDB 两侧**都有**年份。拿不到 NeoDB 侧年份时，整级跳过并记 `unresolved`，不退回「只比标题」。`pickExactTmdbMatch` 的 `expectedYear` 由可选改为**必填**，那个 `expectedYear == null → return true` 的分支被删除。

**为什么**：那个分支是六次已知错写的共同原因。它不是角落里的例外通道，而是**每一轮的常态**：书架端点内联的是 `ItemSchema`，其中没有 `year` / `pub_year`（它们只在条目级 schema 上），所以 `extractNeodbYear` 恒为 `undefined`，那 300 多次标题命中没有一次比过年份。`矿藏之谜` 与 `TMDB 323208` 相差 31 年、`梦境` 与 `635996` 相差 35 年，这行算术一次都没跑过。改参数为必填，是为了让「忘传一个值」变成编译错误，而不是又一次静默放行。

**代价与取舍**：一批「标题唯一但确实没有年份」的条目会从「匹配上」变成 `unresolved`。这是刻意选的：漏配会进待核对名单被人看见，错配不会 —— 而 ⑤ 是唯一写公共 TMDB 数据库的链路，错的是别人条目上的评分。

**配套**：年份从条目自身的 `api_url` 取（`getNeodbItemDetail`），按 uuid 缓存进 `NEODB_ITEM_YEAR_CACHE`。缓存是纯读的目录事实，因此**空跑也回写**（与 `SYNC_STATE_FILE` 不同，后者空跑不写）；丢了只是每个条目多一次请求。取不到年份的两种原因分开记：`no-neodb-year`（目录里确实没有）与 `no-neodb-year-fetch-failed`（读不到），否则一次端点故障会看起来像目录缺口。

**为什么不动控制台文案**：`scripts/review-queue.mjs` 靠 `No TMDB match; skip` 采名单、`verify-log-contract` 锁着它。差异只进留档的 `reason` 与一行 `debug`。

## 12. 第 1 级的外链要验类型，但年份只告警（2026-10-28 立）

**决策**：`external_resources` 里的 TMDB 外链，只有 `mediaType` 与 `category` 推出的类型**严格相等**时才采信；不等则打 `warn`、忽略该外链并降级到第 2/3 级。类型相符但年份相差 > 5 年时只打 `warn`，外链照用。

**为什么分开**：跨类型几乎必然是错 —— `category: tv` 的条目不可能合理地落在 `movie/N` 上（`天涯明月刀·季` 被写进 1976 年的同名电影，正是这条路径）。而年份差可能是正常的：翻拍、重映、合集，以及「整部剧 vs 单集」，都超出搜索容差却仍是同一部作品。

**为什么不因年份推翻外链**：外链是**用户自己**声明的身份。第 1 级是唯一不做任何比较就采信的一级，程序能加的最低证据是类型一致；再往上就该由人决定。

**为什么年份告警只查已知值**：这里能用的年份只有书架载荷（通常为空）或缓存。为本轮约 2 000 条带外链的条目去取目录年份，会让本链路 NeoDB 流量大致翻倍，换来的却是一个**从不改变写入内容**的诊断。真正能拦住写入的是类型闸门；告警是给数据异常留的痕迹，不是防线。

**配套**：`isLinkTypeCompatible` 放在 `rules/tmdb-mapping.ts`（零 I/O），由 `verify:rules` 的三条断言锁住；`getTmdbById` 顺带返回 `year`（复用 `tmdbResultYear`），使告警不需要第二次请求。

## 13. `dropped` 归入 watchlist，不再跳过（2026-10-29 立）

**决策**：⑤ 把 NeoDB 的 `dropped` 与 `progress` / `wishlist` 同等处理 —— 加入 TMDB watchlist，不写评分；`dropped` 同时进入 `SYNC_SHELF_TYPES` 的默认值，排在最后。

**为什么**：TMDB 没有「弃看」态。原来的「跳过」让弃看条目在 TMDB 上完全不可见：既表达不了「不看了」，也丢掉了「这部作品存在过」的事实。加入 watchlist 至少保留后者，并且让映射表少一个特例 —— `dropped` 与「在看」本就同属「不在进行中、也未完成」。

**代价与取舍**：弃看条目与「想看 / 在看」在 TMDB 上无法区分，会留在待看列表；这是明确接受的取舍，写进 README 的边界表，而不是当成 bug。默认多读一个书架、多一轮请求；`dropped` 排在默认列表最后，前三个书架先消耗 `SYNC_MAX_ITEMS`，因此不会挤掉它们。

**配套**：`shelf-not-mapped` 的跳过分支与 `skippedShelf` 计数保留为兜底 —— 当前四种书架都有映射，正常不会命中；`verify-tmdb-mapping` 锁住「加入 watchlist、不写评分、已加入时不重复写」。
